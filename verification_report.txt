rclone-multithreaded-upload v0.0.20 verification report
Date: 2026-09-07

SCOPE
-----
This release changes stage orchestration so cleanup/reservation, trash cleanup,
upload, post-upload cleanup, post-upload trash cleanup, and final verification
have explicit barriers between them. Worker failures remain isolated so one failed
remote does not cancel unrelated remotes.

BASELINE ARCHIVE FINDING
------------------------
The uploaded v0.0.19 ZIP did not contain config.json.

However, its packaged SHA256SUMS, tests/test_logic.py, and old verification report
referred to config.json. This made the original archive's own regression suite fail
1 of 10 tests and made `sha256sum -c SHA256SUMS` report one missing file.

No production config.json was reconstructed or invented in v0.0.20. The packaged
config regression now validates config.example.json, which is actually present.
SHA256SUMS is rebuilt from files actually included in the release.

CURRENT STAGE ORDER
-------------------
1. PRE-UPLOAD preparation for all remotes
   - recursive snapshot
   - cleanup rule planning
   - optional filtered local sizing
   - max_total_size reservation planning
   - combined delete execution

   Global barrier: every preparation worker finishes.

2. PRE-UPLOAD trash cleanup for eligible remotes
   - optional rclone cleanup
   - sleep_after_step

   Global barrier: every eligible trash-cleanup worker finishes.

3. UPLOAD for remotes whose prerequisite stages succeeded

   Global barrier: every upload worker finishes.

4. POST-UPLOAD cleanup for all remotes
   - recursive snapshot
   - cleanup-rule planning
   - max_total_size planning
   - combined delete execution

   Global barrier: every post-upload cleanup worker finishes.

5. POST-UPLOAD trash cleanup for eligible remotes

   Global barrier: every eligible post-upload trash worker finishes.

6. FINAL verification for all remotes

FAILURE ISOLATION VERIFIED
--------------------------
- One PRE-UPLOAD preparation failure does not stop the other remotes from uploading.
- A remote whose PRE-UPLOAD prerequisite failed is skipped for upload.
- One upload failure does not cancel sibling upload workers.
- One POST-UPLOAD cleanup failure does not cancel the other remotes.
- POST-UPLOAD trash cleanup only runs for remotes whose cleanup/delete stage passed.
- Final verification still runs after earlier upload failures in the normal main flow.

SAFETY BEHAVIOR PRESERVED
-------------------------
- Three recursive live snapshots per normal successful remote: PRE-UPLOAD,
  POST-UPLOAD, and FINAL.
- Oldest-first deletion ordering using timezone-aware rclone ModTime.
- Complete-file selection; no partial-file deletion planning.
- Mutable working snapshot removes already-selected paths before later rules.
- Combined deletion plan and one delete command per required delete mode.
- Mixed trash/hard-delete cleanup rule support.
- Deduplicated managed-file union for overlapping cleanup rules.
- Exact reservation deficit selection.
- 1 MiB reservation safety headroom.
- One-byte upload transfer-cap allowance.
- --cutoff-mode CAUTIOUS.
- copy, sync, and move upload command restriction.
- Backend-specific direct-delete flags for Drive, MEGA, and OneDrive.
- Unsupported rclone cleanup treated as a supported skip.
- Post-upload cleanup/final verification continue after failed/partial uploads.
- Per-remote error retention and final non-zero result when a required stage fails.

THREAD LIMITS
-------------
- upload_threads: upload worker pool only.
- trash_cleanup_threads: PRE-UPLOAD and POST-UPLOAD trash-cleanup pools.
- cleanup_threads + remote_quota_cleanup_threads: combined cleanup/quota stages use
  max(cleanup_threads, remote_quota_cleanup_threads), because one snapshot job plans
  both kinds of limits.

FAKE-RCLONE INTEGRATION
-----------------------
The integration test runs the real rclone-multithreaded-upload.py entry point with
a temporary fake rclone executable and temporary remote state.

It verifies:
- both remotes complete successfully;
- exactly 3 recursive lsjson calls per remote;
- identical local source/filter combinations execute one shared rclone size scan;
- no standalone age-delete traversal is used;
- planned delete commands execute;
- both uploads execute;
- final max_total_size state is valid;
- the upload stage does not begin until the slow remote has finished its PRE-UPLOAD
  listing, proving the preparation barrier.

NOT FULLY TESTED
----------------
No destructive test was run against real Google Drive, MEGA, OneDrive, crypt
wrappers, or other live cloud remotes.

The automated environment therefore cannot fully reproduce provider pagination,
rate limiting, throttling, trash semantics, provider-specific permission errors,
network interruption behavior, concurrent external changes to a live remote, or
real long-running rclone transfer timing.

Those behaviors should be tested first with disposable data/test remotes before
production use.
