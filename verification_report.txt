rclone-multithreaded-upload v0.0.22 verification report
Date: 2026-09-10

SCOPE
-----
This release fixes five requested safety/validation issues while preserving the
existing stage barriers, per-remote failure isolation, oldest-first whole-file
planning, reservation headroom, upload transfer cap, and backend-specific hard
delete behavior.

DELETE-LIST COLLISION SAFETY
----------------------------
Generated --files-from names no longer depend only on lossy replacement of ':'
and '/'. remote_name_from_path() now combines a bounded readable fragment with
the full SHA-256 digest of the original remote_path.

Regression coverage proves the former collision example:
- a:b/c
- a_b:c

now produces distinct deterministic filename components.

TRASH VS HARD-DELETE SAFETY
---------------------------
Combined cleanup plans still preserve the delete mode attached to each selected
file and still execute separate rclone delete commands when a plan mixes trash
and hard-delete entries.

Trash cleanup is no longer based only on the upload-level delete_to_trash
default. Per-run result state records actual script-managed trash activity:
- successful reservation-plan trash deletion;
- an actually started rclone sync using trash mode;
- successful post-cleanup-plan trash deletion.

rclone cleanup now requires empty_trash=true plus relevant tracked trash
activity. As a result:
- explicit cleanup-rule trash overrides work even if the upload default is hard;
- hard-delete-only cleanup does not empty unrelated backend trash even if the
  upload default is trash;
- mixed plans preserve both modes;
- an actually started trash-mode sync remains eligible for post-upload trash
  cleanup because sync can delete destination-only files before succeeding or
  failing;
- a configured trash-mode sync that never starts does not set the marker.

DUPLICATE DESTINATION SAFETY
----------------------------
An exact duplicate upload_directories[].remote_path now emits an explicit
WARNING in the config error and refuses to continue. This is intentionally a
validation failure rather than a non-blocking warning because runtime/result
state is keyed by remote_path and concurrent destructive work against the exact
same destination is unsafe.

DELETE_MIN_AGE VALIDATION
-------------------------
load_config() now fully parses delete_min_age before assigning runtime state.
--validate-config therefore rejects malformed durations/timestamps instead of
allowing the error to appear later during cleanup planning.

STRICT SIZE PARSER
------------------
Dedicated application size settings now accept only a whole number immediately
followed by one of:

K, KB, M, MB, G, GB, T, TB

Binary 1024-based multipliers are preserved. Regression tests verify valid forms
and reject malformed/ambiguous forms including G1, 1G2, 1.5M, 1B, 1GiB, and
embedded-space values.

---------------------

delete_min_age validation, malformed size validation, and duplicate destination

NOT FULLY TESTED
----------------
No destructive test was run against real Google Drive, MEGA, OneDrive, crypt
wrappers, or other live cloud remotes. Provider-specific trash behavior,
pagination, throttling/rate limits, permissions, network interruptions,
concurrent live remote changes, and real long-running transfers remain outside
the local automated test environment.
